# Какую модель на какую работу

Две причины разделять, и вторая важнее первой.

**Деньги.** Обход двадцати экранов с замерами — это сотни вызовов
инструментов и почти никакого рассуждения. Платить за него как за решение о
иерархии экрана незачем.

**Контекст.** У субагента он свой и умирает вместе с заданием. Дамп
метаданных Figma на тысячу узлов, вывод аудита по двадцати страницам, три
скриншота на экран — всё это в главном контексте не нужно, а место занимает
навсегда. Главный контекст тратится один раз и не возвращается.

## Таблица

| Работа | Модель | Почему |
|---|---|---|
| Инвентарь живого сайта: обойти страницы, собрать пути и состояния | `haiku` | вызовы инструментов, судить не о чем |
| Прогон `audit.mjs` по экранам, сбор находок | `haiku` | скрипт считает, агент переносит |
| Выемка из Figma: метаданные, переменные, библиотеки | `haiku` | извлечение, не толкование |
| Снятие вычисленных стилей с образцов и подсчёт частот | `haiku` | арифметика |
| Прогон линтера и сборки, сбор ошибок | `haiku` | две команды и разбор вывода |
| Сверка собранного экрана с инвентарём исходника | `sonnet` | сравнение двух списков и суждение о весе |
| Механическая правка по списку: замена дублей на компонент, переименование | `sonnet` | правит файлы, ошибка стоит дорого |
| Проверка экрана глазами: скриншот, «что сломано» | `sonnet` | нужно зрение и суждение |
| Решения о системе, иерархии, тексте, компромиссах контраста | главный контекст | это и есть работа |
| Записи в `DESIGN.md` и отчёт владельцу | главный контекст | голос и обоснования |

`fable` — быстрый и дешёвый, но для сборки интерфейса берётся только на
черновой текст: перечисления, заготовки подписей. Решения им не принимаются.

## Четыре правила делегирования

**1. Делегируется то, что проверяемо машиной.** Контраст, размеры, число
экранов, наличие роли в разметке — да. «Достаточно ли воздуха» — нет: дешёвая
модель ответит уверенно и неправильно, а отличить это от правды по ответу
нельзя.

**2. Задание говорит, что вернуть, и в какой форме.** Свободный пересказ от
субагента бесполезен: его придётся перепроверять целиком. Требовать таблицу
или JSON с полями — тогда результат либо годен, либо явно битый.

**3. Субагент не правит файлы, если задание — не правка.** Разбор и проверка
только читают. Смешанное задание «посмотри и заодно почини» возвращает и
непроверенные находки, и правки, сделанные по ним.

**4. Результат проверяется до того, как на нём что-то строится.** Одна
находка из отчёта — пересчитать самому. Совпало — доверять остальному;
не совпало — перезапустить задание, а не чинить его руками.

## Шаблоны заданий

Форма задания важнее выбора модели: расплывчатое задание портит и `opus`.

### Инвентарь живого продукта — `haiku`

```
Открой <адрес> в браузере. Для каждой страницы, доступной из навигации:
1. адрес и заголовок;
2. главное действие (самая заметная кнопка) — дословно;
3. есть ли поиск, фильтры, пагинация;
4. что показывается, когда данных нет (если удалось увидеть).

Не оценивай дизайн. Верни таблицу: адрес | заголовок | главное действие |
поиск/фильтры | заметка. Ничего не правь.
```

### Замеры по экранам — `haiku`

```
Для каждого адреса из списка: открой, вставь скрипт <путь к audit.mjs>
в javascript_tool, верни его вывод как есть, добавив адрес и тему.
Повтори в тёмной теме (data-theme=dark на корне).
Ничего не интерпретируй и не правь.
```

### Выемка из Figma — `haiku`

```
fileKey=<…>. Верни:
1. список страниц (get_metadata без nodeId);
2. для каждой страницы — узлы верхнего уровня с именами и размерами;
3. переменные (get_variable_defs) по любому экрану — как список
   «имя: значение»;
4. подключённые библиотеки (get_libraries).
Верни JSON. Не пиши код и ничего не оценивай.
```

### Снятие строя с образцов — `haiku`

```
Открой <адреса>. На каждом собери getComputedStyle по видимым элементам:
font-size, line-height, border-radius, height у кнопок и полей, цвета текста
и фона. Верни частоты: значение → сколько раз встретилось, по каждому
свойству, отдельно по сайтам. Не делай выводов.
```

### Сверка с исходником — `sonnet`

Отдельным заданием и **другому агенту, чем тот, кто собирал**. Свою работу
сверяют с исходником плохо: глаз уже знает, что должно быть на экране, и
дорисовывает недостающее.

```
Открой <адрес результата> и <адрес исходника>. Ниже — инвентарь исходника,
составленный до работы: <список по блокам>.

Пройди список строка за строкой. Для каждой верни ровно одну строку:
  перенесено | изменено | потеряно  ·  <элемент>  ·  <что именно видишь>

Считай элементами иконки, логотипы, разделители и вес заливок: «залитая
плитка 48px с белым глифом» и «бледная плитка 40px» — разные элементы.
Не оценивай, что лучше, и ничего не правь. Верни таблицу.
```

Обратный порядок — «посмотри, чего не хватает» без списка — не работает:
агент возвращает впечатления, а не пропуски.

### Проход улучшения — `sonnet`

Этап 7, по экрану на задание. Задание должно **закрыть дверь** тому, что
дешёвая модель приносит охотнее всего — вкусу и уже закрытым замечаниям.

```
Ты старший продуктовый дизайнер. Открой <адрес> и скажи, что здесь можно
сделать ЛУЧШЕ. Правила уже проверены линтером и аудитом — отвечай на
вопрос «а хорошо ли это как продукт».

Смотри: иерархию (что кричит, хотя не важно; что тихо, хотя важно),
пустые обещания (контрол выглядит рабочим и ничего не делает), тексты
интерфейса, состояния, которых нет, но которые случатся, лишнее на первом
экране.

НЕ предлагай градиенты, анимации и «современнее». НЕ повторяй замечаний
про контраст и размеры целей — они закрыты.

Формат: каждая находка ровно тремя строками —
ЧТО: <конкретный элемент>
ЦЕНА: <что теряет человек, одним предложением>
ПРЕДЛОЖЕНИЕ: <конкретная правка>
Не больше восьми, по важности. Ничего не правь.
```

Мало находок — вернуть мало. Добор до восьми ерундой обесценивает первые три.

### Механическая правка — `sonnet`

```
В файлах <список> заменить <что> на <чем>. Ничего кроме этого не менять.
После правки: `npm run build` и `python3 tools/design-lint.py`.
Верни: изменённые файлы, вывод обеих команд. Если сборка не прошла —
откати правку и верни ошибку.
```

## Параллель

Задания, не зависящие друг от друга, запускаются **одним сообщением**: замеры
по экранам, выемка из Figma и снятие строя с образцов — три независимых
задания, и последовательный запуск втрое дольше без единой выгоды.

Зависимые — нет: план строится по разбору, работа по плану.

## Роли видны владельцу

`crew` в `state.js` — не украшение дашборда. Владелец, глядя на результат, не
может отличить работу от везения: строка «Сверщик · sonnet · после каждого
экрана · 4 задания» показывает, что проверка была, а «не запускалась» — что
её не было.

**Если ни одно задание не ушло субагенту — так и написать, с причиной.**
Пустая таблица честнее выдуманной: прогон, где всё шло главным контекстом,
работает, но теряет ровно то, ради чего роли и заведены — независимый взгляд
на свою же работу.

## Чего не делегировать никогда

- выбор дизайн-системы и решения по токенам;
- иерархию экрана и порядок блоков;
- текст интерфейса;
- решение «этот дефект чиним, этот оставляем»;
- разговор с владельцем.

Всё это — работа, ради которой инструмент существует. Делегированное здесь
возвращается уверенным пересказом общих мест.
